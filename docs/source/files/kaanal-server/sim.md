# `kaanal-server/src/sim/`, `control/sim.rs`, `control/sweep.rs` and `control/plan.rs`

The server side of the simulation API. The server depends on `kaanal-sim` for this (a new edge in the crate graph, amending R2.2's direction rule, as the Studio spec section 3 says). User pages: `https://kaanal.naveenr.in/docs/guides/simulate/simulation/`, `https://kaanal.naveenr.in/docs/guides/simulate/traffic/`.

| `control/plan.rs`    | `post_plan` (Step 9c-1): `PlanBody { profile, seed, scenario, target: { multiple } or { req_s }, p99_ms, error_pct, budget_per_hour, keep, max_steps }` with `deny_unknown_fields`. 400 for a bad body or limit (`sweep::limit`), `multiple` outside 0.1..=64, `req_s` not above 0, a stream over `kaanal_sim::MAX_RATE_PER_S` at the target, `max_steps` not 1 to 100 (default 30), a negative `budget_per_hour` (stored as micro-USD), a `keep` name that is not a node; 404 for an unknown profile or scenario; 409 busy, no system, no applied text (no draft source), or an applied text that does not build to the design in force (`ready_to_start`: `same_design` on a blocking thread before the job; message `DIFFERS`, "the design in force differs from the applied text; Apply it (or retry if an Apply just ran)", for a live edit whose structure waits for an Apply, a loader-read file changed on disk, or an Apply under way) (no 429). The flow is the sweep's (`applied_inputs`, the applied text from `Draft.applied`, `to_sim`, `begin_plan` with the seed, fingerprint, `live_chaos`, `chaos_digest`), then on a blocking thread `fill_sizes` and `run_plan`: `same_design` again (an Apply since the route checked fails the job with `DIFFERS`, not as internal), `walk` (each step to `SimStore::plan_step`), `families` (each database not kept: `alternatives(.., with_graph = false)`, a `walk` on each kept flavor with the note "assumes your application can use this family; preset estimates"; an `Err` reason, a dropped flavor or a failed walk is a `skipped` section with its reason), `proposed_text`, `verify`, then one `execute_sweep` of the proposed design (`max_factor` 2k, within 1..=64) for `measured_knee`. Internal failures (`internal: ...`): the draft does not patch or build, the re-check is not the walk's end (`round_trip`, every verdict), or the verdict says `holds`/`already_holds` and the re-check does not hold. A `cannot_hold` verdict with `node: null` (no node saturates) names the crossed limit in its reason. `GET /runs/{id}/report` serves a plan too (`sweep.rs`, `get_run_report`, the `report` dispatch; see [report.md](report.md)), and `GET /runs/{id}/draft` (`get_plan_draft`, in `plan.rs`) serves `proposed_draft` as `text/plain; charset=utf-8`: 404 for an unknown id, 409 for a record that is not a plan, a plan still running, or a failed one (the error says why), 500 for a done plan with no draft (`proposed_draft_of`, unit-tested). Before `begin_plan`, `ready_to_start` checks, cheapest first: `SimStore::running` (409 with the holder's id), a `st.work` permit (429 "too many drafts being built at once; retry", held while the applied text builds), the applied text (409 when empty), `same_design` on a blocking thread (409 `DIFFERS`). After the re-check, `judge_budget` judges the verdict again from `verify.cost` (per-use prices at the target run's visits): `holds` over the budget becomes `over_budget { holds: true }` (`rejudged`), and `budget_check` records the cost against the budget. `claims` includes `over_budget { holds: true }`. Family walks take at most `FAMILY_MAX_STEPS` (10). Step 9c-2: `PlanBody` adds `cheapest`, `time_limit_s`, `run_cap`, `providers`, checked by `plan_search::cheapest_asked` after the `keep` check; `run_plan` dispatches on `PlanAsked.cheapest`: `None` is the walk and `families` as above, `Some` is `run_cheapest` (the main search and the provider sections, no family section); the tail (proposed draft, `verify`, `round_trip` against the search's `end`, the `claims` check, the sweep, `judge_budget`) is shared, and `PlanDoc` gets `cheapest_note`, `search` and `providers`. |

**Draft runs.** `sim/draft_run.rs`: `draft_job(st, req) -> Result<(Job, u64), DraftRunError>` (`Invalid(Diagnostic)`, `UnknownScenario`, `Busy`, `Internal`). It takes a permit of `st.work` (`Busy`, 429), clones the draft's text and `rev`, and on a blocking thread builds it with `build_draft` into a throwaway `Generation` (its `id` is the one in force; it never reaches `AppState`), clones the live `Control` into a scratch value, `remap_control`s it onto the draft by name and compiles the scratch stack (or the named scenario of the scratch set). Nothing is published. `Job.cfg` is a placeholder; `post_run` fills it from `to_sim`. `post_run` branches on `source` (`applied` default, `draft`, else 400), skips `locked` for a draft, maps `Invalid` to 400 `{ error, diagnostic }`, and shares the rest. `RunRecord` gains `source` and `draft_rev`; `Draft.rev` (see [draft.md](draft.md)) is what `draft_rev` records.

**Why the pair.** An Apply swaps the generation under the control lock; `post_run` takes `locked(&st)` first so the chaos snapshot and the generation it names (node ids) belong together. The run then owns an `Arc<Generation>`, so a later Apply cannot change it.

**Caps.** `kaanal_sim::Limits::server()`: 2 000 000 hop records, 5 000 000 simulated hops. Measured on 2026-10-28 (release): a 300 s simulation at 1000 rps (about 300 000 requests) took 0.47 s, and 35 mock requests made during it kept their p99 (22.7 ms against 24.2 ms idle), so the "mock p99 up by 50 ms" trigger for a separate process is not met.

Tests: `tests/sim_http/` (runs, 409, caps, Apply during a run, scenario chaos, errors, blank start, samples; `sweep.rs`: a sweep record to `done`, `kind` on a run, 409 against a run, refused fields, bad limits; `plan.rs`: a plan record to `done`, the Erlang C oracle of three copies, the proposed draft built on a second server, `cannot_hold`, 400/404/409, the draft untouched, one seed one plan, the record's seed, fingerprint and digest, the family section, a dropped flavor, an applied text that is not the design in force as a 409 saying Apply it, a spec changed on disk since the Apply as a 409, no applied text 409, `node: null` when no node saturates, the plan report and draft routes: `plan_report.rs`; `plan_cheapest.rs`: the cheapest record and its search info, strictly cheaper than the walk where the walk leaves unneeded copies, its proposed draft builds and holds, provider sections with the caveat, a provider that cannot translate skipped with the reason, a skipped and an answered section in one record, a section over budget with per-use prices (rejudged), the new fields' 400s, a plain plan's record keys unchanged, `providers: ["none"]`, busy order), unit tests in `sim/profile.rs`, `sim/store.rs` and `sim/plan_draft.rs`, and `mocks_stay_responsive_during_a_run` (`#[ignore]`, by hand in release).

**Skeleton route.** `control/skeleton.rs`: `get_skeleton` reads the draft text, parses it with `Config::from_yaml`, takes the inline `endpoints:` map or reads an endpoints file (`paths::resolve` with `Trust::Api`, so it stays in the project, then `read_text` and `parse_endpoints`), and calls `kaanal_core::skeleton_openapi` on a blocking thread. It does not need a generation, so it answers on a blank start. Core side: [../kaanal-core/spec_skeleton.md](../kaanal-core/spec_skeleton.md).

**Run log.** (A hop line carries `attempt` from `SimReport::hop_attempts`, the try its hop ran in.) `sim/log.rs`: `sample(report, topo, endpoints, cfg) -> LogSample { lines, truncated }` is the one place the sampling rule lives, and it works on a line budget (`MAX_LINES` = 20 000), never on half a request. Failed requests (first 1000 by arrival) then the 500 slowest are taken whole, in that order; if they alone pass the cap the first that does not fit ends the sample (`truncated`). The spread of the rest starts from 4000 minus the kept requests, is shrunk until its lines fit what is left, and keeps its stride (`k * len / n`) across the whole run, so it covers the start and the end alike (`truncated` when it had to shrink). Each request gives a line per hop (`served`, or `queued`/`warn` when the wait exceeds the service; the note is an explicit `hop_label`) plus, for a failure, one `error` line at `arrival + latency` on the failing node with `replica`, `wait_ms` and `service_ms` all `None` (the engine does not record the failing replica). The failure event comes from `RequestRecord.cause` (`kaanal_sim::Cause`, carried from the engine's `FailCause`): `Chaos` is `failed` (note: the failure kind), `RateLimit` is `limited`, `Overflow` is `overflowed`, `Deadline` is `timeout`; nothing is guessed from the status. Lines are sorted by `t_ms`. `Filter` and `page` are pure: `page(lines, filter, after, limit) -> (lines, next)`, `next` being the stored index of the last line returned when more matches follow; a `replica` filter matches only `Some(n)`. Memory: at most 20 000 lines x 8 runs (`RunRecord.log: Arc<LogSample>`). `control/sim.rs::get_run_log` validates `level` (400) and `endpoint` (`endpoint_key`, 400), clamps `limit` to 1..=1000 (default 200), 404 unknown id, 409 while running or when the run failed (no log; the message carries the error); its `note` quotes the `log.rs` constants. Only reported (post-warmup) requests exist in the report, so only they can be logged. Tests: `tests/sim_http/log.rs`, unit tests in `sim/log.rs`.
