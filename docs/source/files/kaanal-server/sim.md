# `kaanal-server/src/sim/`, `control/sim.rs` and `control/sweep.rs`

The server side of the simulation API. The server depends on `kaanal-sim` for this (a new edge in the crate graph, amending R2.2's direction rule, as the Studio spec section 3 says). User pages: `docs/web/simulation.md`, `docs/web/traffic.md`.

| File               | Role                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| ------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `sim/profile.rs`   | `to_sim(&Generation, &RunRequest) -> Result<Planned, SimError>` (`Planned.cfg` is the `SimConfig`). A named profile comes from `Generation.traffic` (a missing one is a 404 that says what to do, `missing_profile`: empty name and no profiles defined, `no traffic profile is defined: add a traffic: section to kaanal.yaml or pass -f profile.yaml (see docs/web/traffic.md)`; empty name with profiles, `no traffic profile named; name one with -p: a, b`; a wrong name, `no traffic profile named 'x'; defined: a, b`; names sorted, at most ten, then `...`), an inline one is checked by `kaanal_core::check_profile`. Each journey becomes a `Stream` (an omitted `resp_bytes` stays 0 until `Planned::fill_sizes` runs, on the blocking thread after the 400 and 409 checks have passed, so a refused request never pays for sampling): rate = `rps × weight ÷ Σweight`, key normalized by `endpoint_key`, `req_bytes` default 0, `resp_bytes` default `sample::sized` (the size of one generated body, seeded; 0 where the mock charges nothing: `HEAD`, `collection:`, a responder without `override`). Duration default 60 s (at most 1 h), warmup default a tenth. An unknown endpoint is a 400 that lists up to five routes sharing its first path segment. |
| `sim/sample.rs`    | `sample(g, key, seed)`: the `override` body, else the schema body from `kaanal_data::generate` with `pins::route_seed(seed or g.seed, owner, path)`, so it equals what the mock generates for the same seed. `find_route` resolves `"METHOD /path/{x}"` through the `matchit` router by turning each `{param}` into `kaanal-x` (a segment no static sibling route is likely to spell, so `GET /a/{x}` is found next to `GET /a/1`). A paged route returns the whole schema body, not a page.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| `sim/store.rs`     | `SimStore`: one run slot (`begin` and `begin_sweep` share the private `begin_kind`, and return the running id when busy), the last eight `RunRecord`s (`kind` `run` or `sweep`; `running`, `done`, `failed`; `generation` is the one the run began on), summaries and the log sample (`log: Arc<LogSample>`, `serde(skip)`, dropped with the run). A sweep's `sweep_points` grow by `sweep_point` as points finish and survive a failure; `finish_sweep` sets `sweep`. `finish` and `finish_sweep` share the private `end` (free the slot, stamp `finished_ms`). `list` strips `summary`, `cost`, `sweep_points` and `sweep`. The lock is never held across a run.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| `sim/run.rs`       | `Job { g, chaos, cfg }`, `check` (the server caps without running, so an oversize request is a 400), `execute_run(&Job) -> Result<(Summary, LogSample), String>` (the only call to `kaanal_sim::run_with_limits`; an out-of-process worker would replace its body, `internal/docs/suggestions/2026-10-28-process-isolation.md`), `execute_sweep(&Job, &Options, on_point)` (the only call to `kaanal_sim::sweep::sweep`, under `Limits::server()`; same rule), and `Slot`, a guard that marks the run failed and frees the slot if the run panics (`finish` or `finish_sweep` disarm it).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| `control/sim.rs`   | `post_run` (parse, take chaos and generation as one pair under the control lock, `to_sim`, `check`, `begin`, `spawn_blocking`, answer `202` + `Location`), `list_runs`, `get_run`, `post_sample`. A named `scenario` is compiled alone with `ChaosStack::set_active` + `compile`; without one the run reads the live `Effective.chaos`. Helpers shared with `sweep.rs` (`pub(super)`): `parse_profile` (name or inline profile, with the record's label), `applied_inputs` (the generation and chaos pair), `accepted` (`202` + `Location`), `busy` (`409 { error, id }`), `from_sim`. `get_run_log` answers `409` for a sweep record (no log).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| `control/sweep.rs` | `post_sweep` (Step 9a): `SweepBody { profile, seed, scenario, p99_ms, error_pct, max_factor }` with `deny_unknown_fields`, so `source`, `duration_s` and `warmup_s` are `400`. `options` checks the limits before anything else: `p99_ms` via `Duration::try_from_secs_f64` and not zero (default 1000), `error_pct` in 0..=100 (default 1, stored as `Limit.error_rate` = pct / 100), `max_factor` in 1..=`MAX_FACTOR` (64, default 8; closes the missing upper bound inside `sweep()`); `target_requests` stays the library default. Then `parse_profile`, `applied_inputs` (always the system in force), `to_sim` with no duration or warmup (the points size their own), no `check` (each point is held to the caps by the sweep), `begin_sweep`, `Slot`, and on a blocking thread `fill_sizes` once, `execute_sweep` with `on_point` writing `SimStore::sweep_point`, `Slot::finish_sweep`. Library side: [../kaanal-sim/sweep.md](../kaanal-sim/sweep.md).                                                                                                                                                                                                                                                                                                            |

**Draft runs.** `sim/draft_run.rs`: `draft_job(st, req) -> Result<(Job, u64), DraftRunError>` (`Invalid(Diagnostic)`, `UnknownScenario`, `Busy`, `Internal`). It takes a permit of `st.work` (`Busy`, 429), clones the draft's text and `rev`, and on a blocking thread builds it with `build_draft` into a throwaway `Generation` (its `id` is the one in force; it never reaches `AppState`), clones the live `Control` into a scratch value, `remap_control`s it onto the draft by name and compiles the scratch stack (or the named scenario of the scratch set). Nothing is published. `Job.cfg` is a placeholder; `post_run` fills it from `to_sim`. `post_run` branches on `source` (`applied` default, `draft`, else 400), skips `locked` for a draft, maps `Invalid` to 400 `{ error, diagnostic }`, and shares the rest. `RunRecord` gains `source` and `draft_rev`; `Draft.rev` (see [draft.md](draft.md)) is what `draft_rev` records.

**Why the pair.** An Apply swaps the generation under the control lock; `post_run` takes `locked(&st)` first so the chaos snapshot and the generation it names (node ids) belong together. The run then owns an `Arc<Generation>`, so a later Apply cannot change it.

**Caps.** `kaanal_sim::Limits::server()`: 2 000 000 hop records, 5 000 000 simulated hops. Measured on 2026-10-28 (release): a 300 s simulation at 1000 rps (about 300 000 requests) took 0.47 s, and 35 mock requests made during it kept their p99 (22.7 ms against 24.2 ms idle), so the "mock p99 up by 50 ms" trigger for a separate process is not met.

Tests: `tests/sim_http/` (runs, 409, caps, Apply during a run, scenario chaos, errors, blank start, samples; `sweep.rs`: a sweep record to `done`, `kind` on a run, 409 against a run, refused fields, bad limits), unit tests in `sim/profile.rs` and `sim/store.rs`, and `mocks_stay_responsive_during_a_run` (`#[ignore]`, by hand in release).

**Skeleton route.** `control/skeleton.rs`: `get_skeleton` reads the draft text, parses it with `Config::from_yaml`, takes the inline `endpoints:` map or reads an endpoints file (`paths::resolve` with `Trust::Api`, so it stays in the project, then `read_text` and `parse_endpoints`), and calls `kaanal_core::skeleton_openapi` on a blocking thread. It does not need a generation, so it answers on a blank start. Core side: [../kaanal-core/spec_skeleton.md](../kaanal-core/spec_skeleton.md).

**Run log.** (A hop line carries `attempt` from `SimReport::hop_attempts`, the try its hop ran in.) `sim/log.rs`: `sample(report, topo, endpoints, cfg) -> LogSample { lines, truncated }` is the one place the sampling rule lives, and it works on a line budget (`MAX_LINES` = 20 000), never on half a request. Failed requests (first 1000 by arrival) then the 500 slowest are taken whole, in that order; if they alone pass the cap the first that does not fit ends the sample (`truncated`). The spread of the rest starts from 4000 minus the kept requests, is shrunk until its lines fit what is left, and keeps its stride (`k * len / n`) across the whole run, so it covers the start and the end alike (`truncated` when it had to shrink). Each request gives a line per hop (`served`, or `queued`/`warn` when the wait exceeds the service; the note is an explicit `hop_label`) plus, for a failure, one `error` line at `arrival + latency` on the failing node with `replica`, `wait_ms` and `service_ms` all `None` (the engine does not record the failing replica). The failure event comes from `RequestRecord.cause` (`kaanal_sim::Cause`, carried from the engine's `FailCause`): `Chaos` is `failed` (note: the failure kind), `RateLimit` is `limited`, `Overflow` is `overflowed`, `Deadline` is `timeout`; nothing is guessed from the status. Lines are sorted by `t_ms`. `Filter` and `page` are pure: `page(lines, filter, after, limit) -> (lines, next)`, `next` being the stored index of the last line returned when more matches follow; a `replica` filter matches only `Some(n)`. Memory: at most 20 000 lines x 8 runs (`RunRecord.log: Arc<LogSample>`). `control/sim.rs::get_run_log` validates `level` (400) and `endpoint` (`endpoint_key`, 400), clamps `limit` to 1..=1000 (default 200), 404 unknown id, 409 while running or when the run failed (no log; the message carries the error); its `note` quotes the `log.rs` constants. Only reported (post-warmup) requests exist in the report, so only they can be logged. Tests: `tests/sim_http/log.rs`, unit tests in `sim/log.rs`.
