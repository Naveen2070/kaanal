# `kaanal-server/src/sim/` and `control/sim.rs`

The server side of the simulation API. The server depends on `kaanal-sim` for this (a new edge in the crate graph, amending R2.2's direction rule, as the Studio spec section 3 says). User pages: `docs/web/simulation.md`, `docs/web/traffic.md`.

| File             | Role                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `sim/profile.rs` | `to_sim(&Generation, &RunRequest) -> Result<Planned, SimError>` (`Planned.cfg` is the `SimConfig`). A named profile comes from `Generation.traffic`, an inline one is checked by `kaanal_core::check_profile`. Each journey becomes a `Stream` (an omitted `resp_bytes` stays 0 until `Planned::fill_sizes` runs, on the blocking thread after the 400 and 409 checks have passed, so a refused request never pays for sampling): rate = `rps × weight ÷ Σweight`, key normalized by `endpoint_key`, `req_bytes` default 0, `resp_bytes` default `sample::sized` (the size of one generated body, seeded; 0 where the mock charges nothing: `HEAD`, `collection:`, a responder without `override`). Duration default 60 s (at most 1 h), warmup default a tenth. An unknown endpoint is a 400 that lists up to five routes sharing its first path segment. |
| `sim/sample.rs`  | `sample(g, key, seed)`: the `override` body, else the schema body from `kaanal_data::generate` with `pins::route_seed(seed or g.seed, owner, path)`, so it equals what the mock generates for the same seed. `find_route` resolves `"METHOD /path/{x}"` through the `matchit` router by turning each `{param}` into `kaanal-x` (a segment no static sibling route is likely to spell, so `GET /a/{x}` is found next to `GET /a/1`). A paged route returns the whole schema body, not a page.                                                                                                                                                                                                                                                                                                                                                               |
| `sim/store.rs`   | `SimStore`: one run slot (`begin` returns the running id when busy), the last eight `RunRecord`s (`running`, `done`, `failed`; `generation` is the one the run began on), summaries only. The lock is never held across a run.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| `sim/run.rs`     | `Job { g, chaos, cfg }`, `check` (the server caps without running, so an oversize request is a 400), `execute_run(&Job) -> Result<Summary, String>` (the only call to `kaanal_sim::run_with_limits`; an out-of-process worker would replace its body, `internal/docs/suggestions/2026-10-28-process-isolation.md`) and `Slot`, a guard that marks the run failed and frees the slot if the run panics.                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| `control/sim.rs` | `post_run` (parse, take chaos and generation as one pair under the control lock, `to_sim`, `check`, `begin`, `spawn_blocking`, answer `202` + `Location`), `list_runs`, `get_run`, `post_sample`. A named `scenario` is compiled alone with `ChaosStack::set_active` + `compile`; without one the run reads the live `Effective.chaos`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |

**Why the pair.** An Apply swaps the generation under the control lock; `post_run` takes `locked(&st)` first so the chaos snapshot and the generation it names (node ids) belong together. The run then owns an `Arc<Generation>`, so a later Apply cannot change it.

**Caps.** `kaanal_sim::Limits::server()`: 2 000 000 hop records, 5 000 000 simulated hops. Measured on 2026-10-28 (release): a 300 s simulation at 1000 rps (about 300 000 requests) took 0.47 s, and 35 mock requests made during it kept their p99 (22.7 ms against 24.2 ms idle), so the "mock p99 up by 50 ms" trigger for a separate process is not met.

Tests: `tests/sim_http/` (runs, 409, caps, Apply during a run, scenario chaos, errors, blank start, samples), unit tests in `sim/profile.rs` and `sim/store.rs`, and `mocks_stay_responsive_during_a_run` (`#[ignore]`, by hand in release).

**Skeleton route.** `control/skeleton.rs`: `get_skeleton` reads the draft text, parses it with `Config::from_yaml`, takes the inline `endpoints:` map or reads an endpoints file (`paths::resolve` with `Trust::Api`, so it stays in the project, then `read_text` and `parse_endpoints`), and calls `kaanal_core::skeleton_openapi` on a blocking thread. It does not need a generation, so it answers on a blank start. Core side: [../kaanal-core/spec_skeleton.md](../kaanal-core/spec_skeleton.md).
