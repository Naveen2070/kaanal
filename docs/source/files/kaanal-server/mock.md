# `crates/kaanal-server/src/mock.rs`

The mock request handler — the axum fallback that serves every non-control route.

## What it does

`handle(State, req)` turns one HTTP request into a mocked response, end to end:

1. **CORS** — preflight (`OPTIONS`) returns 204 with permissive headers and takes **no request id** (it is not logged, and consumes no number). The `/__kaanal` namespace never gets CORS, not even on a 404 (rule R5.4), and no id either.
   1a. **Id and clock** — everything after the preflight check builds a `Flight`: `st.ids.next()` gives the request its `(seq, id)`, the client's `X-Request-Id` is run through `log::client_id` (a bad one is dropped), and the clock starts (`Ident.started`). `Event.ms` / `LogEntry.ms` are measured from here, so they include scope compilation and the login body read. From here on **every** exit tags the response with `X-Request-Id` and ends in exactly one log entry and one event (below).
2. **Routing** — `matchit` lookup by path; 404 `{"error":"no route"}` on miss. Within a matched path, only the exact method matches. A `HEAD` with no entry of its own finds the `HEAD` copy `compile` made from `GET` (own key and counter, rule R6.8; hyper strips the body). No method → 405. Both are answered by `rejected(.., "unmatched")`: the entry has `rejected: unmatched`, no endpoint and no hops, and neither touches a counter.
   2a. **Scope** — `scope_of` reads `X-Kaanal-Scenario` (after the 404/405 checks, so they ignore it; before the login body and the counter, so a bad header costs no draw). A bad header is `400 {"error":"bad scenario scope","detail":...}` with CORS, logged as `bad-scope` (the entry has the route's endpoint and a `null` scope). A good one gives the stack key and its compiled `Scoped` from the cache ([scope.md](scope.md)); no header gives `None`.
   2b. **Login body** — a route whose responder is `Login` and that has no `override` has its body read now, before the chain (`auth::read_login`; no sleep yet), so a bad body still costs the full chain latency. An `override` replaces the responder, so its body is never read.
3. **Plan** — builds a `ChainRequest` (the route's compiled `Endpoint`; per-route atomic counter `n`; `AppState.chain_seed`) and calls `kaanal_core::sample_plan` **in the handler** (microseconds of pure math). `plan_of` samples the whole plan from a scoped request's cached `Scoped` (its chaos and pins; never the live pins) or, without a header, from one `AppState::snapshot()` (an `Arc<Effective>` clone, S10) and its `EffectiveChaos` and `EffectivePins`. It also looks up the pin once: the route's key, or the `GET` key for a synthesized `HEAD`; `resolve(entry, endpoint.states)` settles state, status, body and delay (entry beats `states:` beats defaults), and the delay goes into `ChainRequest.pin_delay`. It returns the plan and the pin's `Outcome`; the snapshot is dropped before the next await, so a swap mid-request never reaches this request, and no lock or mutex is held on the request path.
4. **Engine** — `AppState.engine.run(plan)` hands the plan to the engine actor ([actor.md](actor.md)), which runs it in real time through the shared queues, pools and rate limits and answers with a `Finished` (result, per-hop waits). The client waits the real simulated time. A stopped engine answers 500 `{"error":"engine stopped"}`, logged as `engine-stopped` with the endpoint; the route counter has already advanced and the plan was already sampled (that order predates the log, so it is the one rejection that is not draw-neutral). (Windows caveat: the answer wakes on the OS timer tick, about 15 ms; hops still start at their scheduled times, so the trace stays exact while measured latency can exceed it.)
5. **Response shaping** — a **pin wins (P2)**: with an `Outcome` the reply comes from `pinned_reply` and the chain's verdict is not read (the chain still ran, so hops, queues, tokens and the trace are real). `pinned_response`: `error` answers the pin's status (500 default) with `states.error.body` or `{"error":"pinned","state":"error"}` and `Retry-After: 1` on 429 and 503, never through `error_map` and never a wire failure; `empty` answers the derived body (`pins::empty_form`, path params applied unless it is a verbatim `states.empty.body`) with the pin's or `states:` status or the route's normal success status, except a route that normally answers 204 or 304 keeps that status with no body; `loading`, `slow` and `success` answer as the route normally does (`answer`). Without a pin (`chaos_reply`): on `ChainResult::Err`, a **wire failure** comes first: `reset` or `malformed` at a wire node (`Endpoint::is_wire_node`: gateway or owner), unless the `error_map` has a node or kind key for it, is served by `wire_failure` (below). Otherwise `resolve_error` looks the failure up in the endpoint's `error_map` (node name, then failure kind, then exact status, then class such as `5xx`); with no match the kind's default status (own status, reset/malformed 502, timeout 504) and `default_error_body` (`{"error":"chaos","node":name}`, plus `"kind"` for a non-status kind) are used. A `timeout` at a wire node is not a wire failure: it stays remappable. A final status of **429** from a rate limit carries `Retry-After` (whole seconds, rounded up, at least 1); an `error_map` that changes the status drops it. Precedence: chain failure (through `error_map`) > `override` > built-in responder (413/415/400, then 401 or 200; the JWKS is 200; a JWKS `HEAD` answers through its synthesized copy) > generated body. On `Ok`: the endpoint's `override` (status and body) if it has one, else the responder's answer (`auth::respond`), else `kaanal_data::generate` seeded by `stable_hash(seed, node, path)` (same `seed:` + URL → same body forever; a new `seed:` reshuffles the data; the chain seed is not involved), then `apply_params` copies path params into matching fields.
   5a. **No-store** — every response of a `Login` route (including chain failures and an `override`) gets `Cache-Control: no-store` and `Pragma: no-cache`. The JWKS does not.
   5b. **Scope echo** — a scoped response gets `X-Kaanal-Scope: <names joined by ,>` (the deduplicated stack; an empty header echoes an empty value). No header, no echo. `with_cors` exposes it.
6. **Trace header** — `X-Kaanal-Trace`, built by `record::trace_parts` ([record.md](record.md)) from the plan and the engine's finished hops: the visible hops in plan order with one decimal (`nginx.proc=1.0ms,net=1.0ms,db.read=1.0ms`); cache lookups print `cache.hit=` or `cache.miss=`; a hop that queued is preceded by `node.wait=T` (for example `app.proc=2.0ms,net=1.0ms,db.wait=98.0ms,db.read=100.0ms`; none at zero load, and a wait piece counts as a hop in `...+N hops`); a `parallel` block is bracketed with `|` between branches, e.g. `nginx.proc=1.0ms,net=0.0ms,app.proc=2.0ms,[net=0.0ms,audit.proc=1.0ms|net=0.0ms,pay.proc=4.0ms],net=0.0ms,c.hit=0.2ms`; a pin's delay is the first piece, `entry.delay=10000.0ms`; a failure appends `node.error=STATUS` (the real failure, even when `error_map` changed the response status), or `node.error=reset` / `malformed` for those kinds; an endpoint `Delay` hop prints `entry.delay=`. Branches a failure cancelled show only what they ran before the failure instant (a branch that never started is empty). The header value is capped at 4096 bytes: past that it stops before a hop, closes any open `[`, and ends `,...+N hops` with N the pieces left out, wait pieces included (ASCII, D13); the error part and the final `pinned=STATE` piece (present on a pinned request) are always kept, so both are reserved before the hops are cut. The log keeps the same text uncapped up to 16 KiB.
7. **Log entry and event** — `finish` builds the `LogEntry` with `record::build_entry` (flags, hops, `chain_error`, see [record.md](record.md)) and `publish` pushes it into the ring **first**, then sends the bus event built from it (`record::event_of`), so a subscriber that sees the event can already fetch the entry. The event carries id, client id, seq, `rejected`, timestamp, method, path, endpoint, status, **measured** wall ms, ordered unique node names (the failing node too, even under a pin), failing node, `kind`, `pin` and `scope`, on the broadcast bus for SSE subscribers. No subscribers = send error, ignored by design. `x-request-id` is set on the response by `tag` before it is returned.
   7a. **Client gone** — if the client closes the connection, hyper drops the handler future. `Flight::drop` then publishes a `client-gone` entry (status 499, no hops, the endpoint if routing had got that far) and its event, so every id ends in an entry. Every normal exit takes the `Ident` out of the `Flight` first, which disarms it. A panic unwinding through the handler is not a client abort: the drop sees `thread::panicking()` and logs nothing.

## Wire failures (B2a)

`wire_failure` serves a `reset` or `malformed` at a wire node. Both start from the real reply (`answer()`: responder or success body, so the JWKS is cut as the JWKS) and the route's success status:

- **malformed** — the serialized body cut at about half at a char boundary, `Content-Type: application/json`, correct `Content-Length`: valid HTTP, invalid JSON.
- **reset** — `wire::Cut` streams one chunk, then breaks; `Content-Length` is the full length (at least chunk + 1), so the client has the status line and part of the body and then sees the connection abort ([wire.md](wire.md)).
- **Nothing to cut.** No body, or HEAD / 204 / 304 (hyper strips the body): the plain success response; the trace still ends `error=reset|malformed`. A body-less success route (`null`) breaks as `{}`.
- The event's status is the status actually sent, and the entry's `kind` is `reset` or `malformed` (the status stays 200).

## Other items

| Item                                                             | What it does                                                                                                                                                                                                                                                                    |
| ---------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `with_cors(resp)`                                                | Adds `Access-Control-Allow-Origin: *`, methods, headers, and exposes `x-kaanal-trace`, `x-kaanal-scope`, `x-request-id` and `retry-after`. Mock routes only: every return in `handle`, the final one included, goes through the `cors` closure, which skips it for `/__kaanal`. |
| `response(status, body, trace, retry)`                           | Builds the reply: status, JSON body (none for `null`), `x-kaanal-trace`, and `Retry-After` for a 429.                                                                                                                                                                           |
| `generated_body(st, route, owner, path, params)`                 | The spec-schema body of a successful route (`null` without a schema).                                                                                                                                                                                                           |
| `success`, `plan_of`, `answer`, `default_error_body`             | Helpers extracted from `handle` (clippy `too_many_lines`): the success reply, the plan sampling call (passes `ep.key` for endpoint-scoped chaos; takes the scoped stack when there is one), responder-or-success, the default error body.                                       |
| `chaos_reply`, `pinned_reply`, `pinned_response`, `Reply`, `Ask` | The reply builders split out of `handle`: the chain verdict through `error_map` and the wire rules, or a pin's answer. `Reply` carries status, body, failed node, `Retry-After` and a wire response; `Ask` the method, path and path params.                                    |
| `scope_of`, `bad_scope`, `engine_stopped`                        | The request's scope key and compiled stack (`Err` is the 400 detail), the 400 body, and the 500 for a stopped engine.                                                                                                                                                           |
| `no_store(resp)`                                                 | Adds `Cache-Control: no-store` and `Pragma: no-cache` (login routes).                                                                                                                                                                                                           |
| `Flight`, `Ident`                                                | The request in flight (see 1a and 7a): the armed guard with the method, path and endpoint it has found so far, and the `Ident` (`id`, `client_id`, `seq`, `started`) whose `facts` method turns it into the entry's `Facts`, measuring `ms` at that moment.                     |
| `finish`, `Served`                                               | Everything after the engine answered: trace parts, reply (pin or chain), `no_store`, `tag`, scope echo, the touched nodes, the entry and `publish`. Split out of `handle` for the 100-line limit.                                                                               |
| `rejected(st, ident, method, path, endpoint, why, resp)`         | Tags and logs a response that no chain produced (`unmatched`, `bad-scope`, `engine-stopped`).                                                                                                                                                                                   |
| `publish(st, entry, nodes)`, `tag(resp, id)`                     | Ring push then bus event; the `X-Request-Id` header.                                                                                                                                                                                                                            |
