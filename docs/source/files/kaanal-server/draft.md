# `crates/kaanal-server/src/draft/mod.rs`

The Studio draft: the text of the `kaanal.yaml` being edited, apart from the running system.

## What it does

The draft is canonical YAML text, so comments, order and line endings survive an edit (Studio step 2, spec section 5). Replacing it, or patching it, touches neither the running system nor the disk; Apply and Save are what do. One draft per server, last writer wins (single user).

## Types

| Item              | Kind   | What it does                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| ----------------- | ------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `MAX_DRAFT_BYTES` | const  | 1 MiB (1048576): the longest text `PUT /draft` accepts.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| `DraftSource`     | struct | `file` and `text`: what a draft starts from. `kaanal up` passes the config file and the text it read; exported through `ServeOpts.draft`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| `Draft`           | struct | `text` (being edited), `applied` (the text of the generation in force), `file` (what Save writes, made absolute at start; `None` with no source), `base` (what the file held when we last read or wrote it: Save compares the disk with it; `None` when the file did not exist), `lost` (what patches could not keep, until the text is replaced whole) and `rev` (starts at 0, +1 on every change of `text`, whole-text PUT or patch; `GET /draft` shows it and a draft simulation run records it as `draft_rev`). `Draft::from_source(Option<DraftSource>)` starts clean, or empty with no source; `dirty()` is `text != applied`. Held in `AppState.draft` (`Mutex<Draft>`). |

`draft/apply.rs` turns draft text into a system:

| Item                                                 | Kind   | What it does                                                                                                                                                                                                                                                                                                                                                    |
| ---------------------------------------------------- | ------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `Diagnostic`                                         | struct | One problem placed in the draft: `file` (when not `kaanal.yaml`), `line` (1-based), `col` (0-based), `path` (`["edges", 1, "to"]`), `message`.                                                                                                                                                                                                                  |
| `build_draft(text, dir, drawn_seed, auth_key, port)` | fn     | `Config::from_yaml`, then `Generation::build` with `Trust::Api` (paths confined, lenient scenario files) and the auth issuer (so a draft with an auth node and no key fails in validate as in Apply), with no engine started; returns the generation and its scenarios, or the first problem as a `Diagnostic`. Apply (T6) builds the same way before it swaps. |

`draft/patch.rs` turns the UI's edits into splices:

| Item               | Kind   | What it does                                                                                                                                                                                                                                                                                                                                                                              |
| ------------------ | ------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `Op`               | struct | One `{ op, path, value }` of a patch (`op`: `set`, `insert`, `append`, `remove`, `swap`; `swap` also takes `with`, the second item's path). A path is keys (text) and list indexes (numbers); for `insert` its last step is the new key (quoted by `splice` when not plain). `value` is read as YAML so an object keeps the order sent; `null` is a value, a missing `value` is an error. |
| `apply(text, ops)` | fn     | Maps the operations to [`kaanal_core::splice`](../kaanal-core/splice.md) edits and applies them: returns the new text and `lost`, or a message (bad operation, nothing at the path, key already there, not YAML).                                                                                                                                                                         |
| `render` (private) | fn     | A value as YAML in the project's flow style: bare words where safe (including durations like `2ms`), JSON quoting where a bare word would change meaning (`yes`, `8`, `1e3`, `0xab`, empty), `{ a: 1 }` and `[a, b]`.                                                                                                                                                                     |

`draft/save.rs` writes the draft to its file:

| Item                                               | Kind   | What it does                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| -------------------------------------------------- | ------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `SaveError`                                        | enum   | `Lost(Vec<String>)`, `Conflict`, `NoFile`, `Plan(String)` (the draft does not build, so its scenario files cannot be chosen), `Io(String)`: why nothing was changed.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| `Change`                                           | enum   | `Write(path, text)` or `Delete(path)`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| `Saved`                                            | struct | `written` (the config's file name), `removed` (`scenarios/NAME`), `layout_written` and `layout_note` (see `layout.rs` below).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| `save(draft, once, confirm_loss, overwrite, plan)` | fn     | Saves one at a time (`once` is `AppState.save_lock`) and holds the draft lock only to snapshot and to record the outcome, never across disk work. From the snapshot: `NoFile`, then `Lost` unless `confirm_loss`, then `Conflict` when the file's text (a link is followed) is not `base` (changed, deleted, or created behind us) unless `overwrite`; then `plan(text)` (the route first runs `paths::confine` on it, so a draft naming a file outside the project is `Plan` -> 400) names the files to delete for exactly that text; the deletions and then the config (last) are committed, `base` becomes the text and `lost` clears (unless a `PUT` changed the text meanwhile: the newer text stays and still owes its `lost`). The comparison is of text, not of mtime or a hash: it is exact, and a `touch` is not a conflict. |
| `commit(changes, rename)`                          | fn     | Every change or none: stages every `Write` as a temp file in its folder (`.NAME.kaanal-PID-NANOS-N.tmp`: unpredictable, opened with `create_new` so nothing already there is followed or reused; flushed with `sync_all`; the target's permissions set through the open handle), then makes the changes in order, each remembering what it replaced; a file that cannot be read stops it before it changes anything; if one fails the earlier ones are restored (a file that could not be put back is named in the error) and the temp files removed. A single file is replaced by rename, so a reader sees the old or the new one. `rename` is a parameter so a test can fail it.                                                                                                                                                     |

The route (`control/draft.rs`) adds `fix_scenarios`: `remove` is the `plan`: it builds the saved text and keeps the `flagged` scenario files that are regular files (not links) directly in the project's own `scenarios/` folder (`stale_scenarios`, by `Flagged.path`, not by the name shown to clients); `rewrite` is 400 until rename exists.

`draft/gate.rs` is the admission gate Apply uses to stop mock traffic for the length of a drain:

| Item                     | Kind     | What it does                                                                                                                                                                                            |
| ------------------------ | -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `Gate`                   | struct   | Counts the mock requests in flight and can hold new ones back. `AppState.gate`.                                                                                                                         |
| `Gate::enter()`          | async fn | Waits while the gate is paused, then counts the request in; the returned `Entered` guard, held until the answer is built, counts it out on drop. A request that only waits does not count as in flight. |
| `Gate::pause()`          | fn       | Holds new requests back until the returned `Paused` guard drops (on every path out of an Apply, including a panic).                                                                                     |
| `Gate::drained(timeout)` | async fn | Waits until nothing is inside, at most `timeout`; true when drained.                                                                                                                                    |

The order that makes it safe: `enter` counts itself in first and reads the flag second; Apply sets the flag first and reads the count second, so a request is either seen by the drain or sees the pause.

`draft/apply.rs` also holds `apply(st, timeout)`, which builds the draft, pauses the gate, drains, swaps and resumes. The locks it takes, in order: `apply_lock` (one Apply at a time), the gate, then the `control` lock for the swap, under which the chaos state, the scenarios and the generation change together. `ApplyError` is `Invalid(Diagnostic)`, `Timeout` or `Internal`. The swap keeps chaos, runtime scenarios, leases and pins by name through `remap.rs`; scenario files that no longer resolve are flagged. The `control` state is cloned first and put back if the publish fails (the old generation stays, so its control state must), and the collections are emptied with the swap. `MAX_DRAFT_BODY` (about 6 MiB) is the body limit of the draft routes, looser than the 1 MiB text limit so a text of escapes is judged by the text limit.

`draft/remap.rs` keeps what still applies across an Apply:

| Item                                          | Kind   | What it does                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| --------------------------------------------- | ------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `remap_control(old, new, scenarios, control)` | fn     | Rebuilds the `Control` state for the new generation under the control lock: live chaos and chaos leases through a name-based `KeyMap` (node by name, edge by its two node names, a replica only while it exists, an endpoint only while it has an entry node), the runtime scenarios (remapped like live chaos; the draft's definition wins on a name clash), the active scenarios the new set still defines (with their activation leases), and the live pins the API would still accept (not a synthesized `HEAD`, has an entry node, an `empty` pin still has a form). A `bandwidth_cap` the new edge cannot take is removed (`drop_stale_caps`). Returns a `Report`, or an error (the active stack could not be rebuilt) with `control` untouched. |
| `Report`                                      | struct | `kept` (`{ live_chaos: n, active_scenarios, runtime_scenarios, pins: n }`) and `dropped` (`{ live_chaos: [labels], scenario_chaos: [labels], active_scenarios, pins }`), the shapes of the Apply answer.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |

`Generation::build` takes a `lenient` flag for this: a scenario _file_ that does not resolve against the new topology is left out and listed in `Generation.flagged` (a [`Flagged`](generation.md)) instead of failing the build; startup and `check` stay strict.

What a client gets back never shows the machine's layout: `Diagnostic.file`, the `flagged` files and the project folder inside messages and warnings (`scrub`, in both the spelling given and the loader's canonical one) are made relative (`relative`, which also understands the canonical folder), and the CLI cleans a server-supplied file name like every other string.

The routes are in [control.md](control.md) (`draft.rs`); the HTTP contract is in [docs/web/control-api.md](../../../web/control-api.md#draft).

## Blank start, add_node and rename_node

- `BLANK_TEXT` (`version: 1\nnodes: {}\n`) is the draft of a blank start; `Draft::blank(file)` makes it: nothing applied (so it is dirty), `file` made absolute, `base` what `file` holds now (`None` when it does not exist, so a file that appears before Save is a conflict). `serve_blank(base_dir, file, opts)` (see [lib](lib.md)) starts with `AppState::blank`.
- `Draft.renames` records the `rename_node` operations since the text was set (a whole-text `PUT` clears it, so does a Save that rewrote files). Save's `fix_scenarios: rewrite` applies them.
- `patch.rs`: `Op` also takes `name`, `kind` (`add_node`) and `from`, `to` (`rename_node`); `apply` now runs the operations one at a time, each on the text the last left (a rename needs it), and returns `Applied { text, lost, touched, notes, renamed }`. `add_node` is an `Insert` under `nodes` of `presets::starter(kind)`. A rename whose edits report anything in `lost` (an anchored reference) is refused whole.
- `rename.rs`: `plan(text, from, to)` lists the places a node name is written (see the [control API](../../../web/control-api.md#draft)) from `splice::scalar_paths` and returns the edits (`RenameKey` for the `nodes:` key and `error_map` keys, `Set` for the references), a label for each, and notes for files it does not reach. `rewrite_scenario(text, renames)` applies recorded renames, in order, to a scenario file's `chaos[].node` and `chaos[].edge` ends; `None` when it names none of them, an error when a name is in an anchored value.
- `save.rs`: `Plan { remove, rewrite }` is what a Save does besides the config; `plan` now also gets the renames. Rewritten files are listed in `written` as `scenarios/NAME`.

## The layout sidecar (`draft/layout.rs`)

Node positions for Studio's canvas, kept out of `kaanal.yaml` in `kaanal.layout.json` beside it. A new write path, so it is held to the confinement rules of Save: a fixed name (no input reaches the path), the folder is the config file's own, the same `commit` (temp file with `create_new`, then rename), and a link or non-regular file is never followed nor replaced. Last writer wins (no `base` or conflict check: positions are low-stakes).

| Item                                                 | Kind   | What it does                                                                                                                                                                                                                                                                                                                                                                                                                               |
| ---------------------------------------------------- | ------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `FILE`, `MAX_FILE_BYTES`, `MAX_ENTRIES`, `MAX_COORD` | const  | `kaanal.layout.json`; 256 KiB; 2000 positions; ±1e6.                                                                                                                                                                                                                                                                                                                                                                                       |
| `Layout`                                             | struct | `BTreeMap<String, [f64; 2]>` (serde-transparent). `check()` (entries, empty name, finite and in range, file size), `rename(from, to)`, `of_nodes_in(text)` (only the nodes a valid config text defines; everything when it is not one).                                                                                                                                                                                                    |
| `load(dir)`                                          | fn     | The layout and a note. Missing: empty, no note. Otherwise `symlink_metadata` must say regular file; the open does not follow a reparse point (Windows, `FILE_FLAG_OPEN_REPARSE_POINT`) or must be the same `(dev, ino)` as what was looked at (Unix); size checked on the handle and the read capped at 256 KiB + 1; `deny_unknown_fields`, `version` 1, `check()`. Any failure: empty layout and a note naming only `kaanal.layout.json`. |
| `save(config, dir_before, layout, text)`             | fn     | Called by `save::save` after the config is committed. Drops positions the text does not define; empty writes nothing. The folder must canonicalize to `dir_before` (taken before the config write); the sidecar must be absent or a regular file (`symlink_metadata`); then `commit` of one `Write`. Returns `(written, note)`; never undoes the config.                                                                                   |

`Draft` gains `layout` and `layout_note`, read by `from_source` and `blank` (from the config file's folder). Layout edits never change `rev`. `GET /draft` shows `layout` (filtered to the nodes of `doc` when the text is a config) and `layout_note`; `PUT /draft` takes `layout`, alone or with `text`/`patch`, checked before the lock; `rename_node` moves the key. A successful sidecar write clears `layout_note` and sets `saved_layout`; `layout_dirty` (shown by `GET /draft`) is `layout != saved_layout`.
