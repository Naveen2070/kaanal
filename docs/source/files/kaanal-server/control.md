# `crates/kaanal-server/src/control/`

The control API handlers and the security guard that stands in front of them.

## The guard (runs before every `/__kaanal/*` route)

`guard(State, req, next)` — a middleware, so it runs **before any extractor parses a body or query**; unauthenticated callers never reach handler code:

1. **Host check** — `host_allowed(host, port)`: must be `localhost`, `127.0.0.1` or `[::1]`, with no port or the bound port (DNS-rebinding guard, rule R5.3). Case-insensitive; IPv6 bracket parsing; rejects tricks like `localhost.evil.example` and `evil.example:8080@localhost`. Failure → 403.
2. **Token check** — every path except `/__kaanal/health` and `/__kaanal/ui` needs `Authorization: Bearer <token>`. `/__kaanal/events` alone may take `?token=` because the browser `EventSource` API cannot set headers (rule R5.2). Comparison is `ct_eq` — constant-time, so the token can't be guessed byte-by-byte from response timing. Failure → 401.
3. **Response hardening** — `Cache-Control: no-store` and `X-Content-Type-Options: nosniff` on every control response.

## The one write path (S11)

Every handler that changes chaos state does the same three things:

1. `lock(st)` the `Control` mutex (a poisoned lock is recovered with `into_inner`, so one panic does not take the control plane down). The guard is never held across an `.await`; the compiler enforces it because the handler futures must be `Send`.
2. `commit(st, &mut guard, |control| ...)`: back up `Control`, run the closure, then `AppState::publish` (compile, check, swap the `Arc`). On an error from either, the backup is put back, so a bad request changes nothing. A panic is not caught: the half-written `Control` would be compiled by the next write, while the request path keeps the last published `Arc`.
3. Answer from the `Arc<Effective>` that `commit` returned (exactly what was published) and `emit` a scenario event where the stack changed.

`commit` also drops every lease whose scenario is no longer active (`Control.leases.retain`), so a lease never outlives its activation or its scenario, and runs `chaos_lease::prune`, so a chaos lease never outlives its live field ([chaos_lease.md](chaos_lease.md)). `AppState::publish` then clears the scoped-stack cache on every publish ([scope.md](scope.md#publish-clears-the-cache-every-time)). **Lock order:** `control` first, then the scoped-cache write lock; the request path takes the cache read lock alone.

Only writers and the two scenario GETs (`list_scenarios`, `get_scenario`, whose data lives in the set) take the mutex. The request path and the other GETs read the snapshot.

**Link chaos (1d).** `ChaosPatch` and `KeyedPatch` take `jitter_ms` and `bandwidth_cap` (a number, or a string with a unit such as `"500KB/s"` read by `kaanal_core::units::bandwidth_cap`; a bad string is a 422 from the JSON extractor, a zero after conversion a 400 from `check`); `KeyedPatch` takes `edge: { from, to }` and `DELETE` takes `edge_from` and `edge_to` (`edge_key` resolves them: 400 mixed with a node, endpoint or replica or half an edge, 404 unknown node or edge). `apply_patch` runs `ChaosLayer::check_link` on an edge key against the edge's bandwidth and rejects link-only fields on any other key. `view.rs` lists edges under `edges` as `{ edge: { from, to }, ... }`, shows `jitter_ms` and `bandwidth_cap` only when set, and writes them in saved scenarios.

## One generation per handler

A handler that needs the system (chaos, scenarios, pins, topology, `scenarios/save`) takes the [`Gen`](generation.md) extractor, so it reads the topology and endpoints of one generation from start to end; helpers such as `keyed_json`, `key_label` and `apply_patch` receive it as `&Generation`. With no generation the extractor answers 409 `{"error":"no system applied yet; apply a draft"}` (covered by the extractor's unit test; a handler-level test comes with the blank start, step 2d). `POST /reset` and the lease task work without one (nothing to zero, no chaos to expire).

## `lock_gen`: a handler and an Apply cannot interleave

A handler that resolved something against its generation (a scenario or pin against the topology, a chaos key against the node list) takes the control lock with `lock_gen(st, g)` instead of `lock(st)`. It answers 409 `the system changed while this request ran; retry` when an Apply put another generation in force since the handler took `g`. Apply swaps under the same lock, so once `lock_gen` succeeds the generation cannot change before the lock is released. The reads that pair the control state with the generation (`get_chaos`, `get_active`, `get_scenario`) use `locked(st)` instead: lock first, then read the generation, so they answer from whichever generation is in force and never refuse a swap (409 only when there is no system at all).
