# `crates/kaanal/src/main.rs`

The `kaanal` binary: clap CLI, process lifecycle, and a thin HTTP client for the control API. Usage errors exit 64 (`sysexits` `EX_USAGE`), not clap's default 2, because 2 means "not running" (R6.3 as amended by R1.45); `--help` and `--version` exit 0. Every error and warning line goes through `clean()` before it reaches the terminal.

## What it does

Two kinds of commands:

- **Local**: `up` (run the server; with `-d`, start it in the background), `down` (stop it), `validate` (dry-run the config), `schema` (print the JSON Schema) and `endpoints` (skeleton entries for spec routes).
- **Remote**: `status`, `chaos set|clear`, `scenario ...`, `cycle`, `pins`, `reset`, `logs` and `trace` — thin clients that find the running instance via `.kaanal/run.json` (after checking the instance lock, see [lifecycle.md](lifecycle.md)) and call its control API (rule R2.6: no per-interface logic). `status` prints a 12-wide TYPE column so `external-api` fits. The one exception to "thin" is `scenario load`, which parses the file here (with core's `parse_scenario`) so a mistake shows as `file:line:col`.

| `endpoints:` in kaanal.yaml | No `--write`     | `--write`                                                                                                  |
| --------------------------- | ---------------- | ---------------------------------------------------------------------------------------------------------- |

| absent                      | Prints the block | Creates `kaanal.endpoints.yaml` and says which line to add; refuses if that file already exists            |
| every route covered         | `nothing to add` | `nothing to add`                                                                                           |

## Exit codes (rule R6.3)

`0` ok · `1` error · `2` not running (no `run.json`, or the instance there is gone) · `3` reserved for assertion failures (no command returns it yet) · `64` usage error. Carried by `Fail(u8, String)`; `main` prints the message to stderr and returns the code. `Fail::usage(msg)` makes a 64: every bad argument the CLI detects **before** it sends a request (bad latency or rate, `--ttl`, `--state`, `--delay`, `--from`, `-n` range, empty `--scope`, `--since` and `--status` in both `logs` modes, `chaos set` with nothing to set, scenario names and file names). clap's own errors are turned into 64 in `main` (`Cli::try_parse`; `--help` and `--version` stay 0). A value the server refuses (HTTP 400) stays 1. Table for users: [../../../web/lifecycle.md](../../../web/lifecycle.md#exit-codes).
