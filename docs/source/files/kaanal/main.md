# `crates/kaanal/src/main.rs`

The `kaanal` binary: clap CLI, process lifecycle, and a thin HTTP client for the control API (local, or a remote instance through `--endpoint`). Usage errors exit 64 (`sysexits` `EX_USAGE`), not clap's default 2, because 2 means "not running" (R6.3 as amended by R1.45); `--help` and `--version` exit 0. Every error and warning line goes through `clean()` before it reaches the terminal.

## What it does

Two kinds of commands:

- **Local**: `up` (run the server; with `-d`, start it in the background), `down` (stop it), `validate` (dry-run the config), `schema` (print the JSON Schema), `endpoints` (skeleton entries for spec routes), `demo` (the embedded demo project, run as `up` runs) and `completions SHELL` (a shell completion script on stdout; needs no instance and ignores `--json`).
- **Remote**: `status`, `chaos set|clear`, `scenario ...`, `cycle`, `pins`, `reset`, `logs` and `trace` — thin clients that find the running instance via `target::resolve` (`.kaanal/run.json`, or a remote one, below) (after checking the instance lock, see [lifecycle.md](lifecycle.md)) and call its control API (rule R2.6: no per-interface logic). `status` prints a 12-wide TYPE column so `external-api` fits. The one exception to "thin" is `scenario load`, which parses the file here (with core's `parse_scenario`) so a mistake shows as `file:line:col`.

## Global flags and remote mode

Three flags are declared on `Cli` with `global = true`, read once in `main` and handed to [output.md](output.md) and [target.md](target.md):

- **`--json`** (also `KAANAL_JSON=1|true`): before or after the subcommand. Read commands print the server's JSON as one line through `output::emit`; write commands print the body the server returned, nothing for a 204. `logs` and `trace` no longer declare their own `--json`; their output is unchanged. It never changes behaviour or exit codes; errors stay text on stderr.
- **`--endpoint URL`** (also `KAANAL_ENDPOINT`): before or after the subcommand. `logs`, `chaos set`, `chaos clear` and `cycle` name a route key `--route` (`cycle` positionally; the `Cli` field `endpoint` and a subcommand field of the same name would share one clap id). clap rejects a hidden `--endpoint` alias next to the global flag, so the old route-key spelling arrives as the global flag; `Cli::fix_route` moves a value containing a space (a route key is `METHOD /path`, an address has none) into the route slot, for one release, and makes `chaos set` without node or route a usage error. With an endpoint the client never reads `run.json` or the lock.
- **`--token T`** (also `KAANAL_TOKEN`; the help text says a command-line value shows in process lists). Only the flag without an endpoint is a usage error; an exported `KAANAL_TOKEN` alone is ignored.

Remote failures are exit 1 (`cannot reach ...`, `token rejected`), never 2. `up` and `up -d` refuse an endpoint from either source with a 64 (`no_endpoint`).

## Exit codes (rule R6.3)

`0` ok · `1` error · `2` not running (no `run.json`, or the instance there is gone) · `3` reserved for assertion failures (no command returns it yet) · `64` usage error (also a bad `--endpoint`, a missing token, `--token` without an endpoint, `up` with an endpoint; remote failures are 1, never 2). Carried by `Fail(u8, String)`; `main` prints the message to stderr and returns the code. `Fail::usage(msg)` makes a 64: every bad argument the CLI detects **before** it sends a request (bad latency or rate, `--ttl`, `--state`, `--delay`, `--from`, `-n` range, empty `--scope`, `--since` and `--status` in both `logs` modes, `chaos set` with nothing to set, scenario names and file names). clap's own errors are turned into 64 in `main` (`Cli::try_parse`; `--help` and `--version` stay 0). A value the server refuses (HTTP 400) stays 1. Table for users: [../../../web/lifecycle.md](../../../web/lifecycle.md#exit-codes).

A reader thread splits the stream into SSE messages and queues them on a bounded channel (`logview::BACKLOG`, 4096), counting what does not fit; only then it fetches the tail (`GET /logs`), prints it and records the ids in `Seen` (last 2000). `logview::drain` then prints every queued `request` event that `Seen` has not met and `passes` the filter; with `--json` it fetches the full entry (`GET /trace/{id}`) first. A `lagged` notice goes out whenever drops were counted. Ctrl+C exits 0 from its own thread; a `shutdown` event (a `down` or signal drain) makes it wait for the lock to go (the event's `timeout_ms` plus 2 s) and exit 2 with `kaanal stopped (the server shut down)`; a stream that ends without one waits up to 2 s for the lock, then goes through `transport_failure`: exit 2 when the instance is gone, exit 1 `kaanal is running (pid N) but its control API did not answer` when the lock is still held. |
