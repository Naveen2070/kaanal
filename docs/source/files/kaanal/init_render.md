# `crates/kaanal/src/commands/init/render.rs` (private)

The text `kaanal init` writes, split out of `init/mod.rs` (a folder module; code moved, not rewritten). Pure functions, no I/O. RULES 57.

## Items

| Item              | What it does                                                                                                                                                                                                                                                                                                                                                                           |
| ----------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `Style`           | The server style answer: `EventLoop` or `ThreadPerRequest`. `Style::parse` takes exactly `event-loop` or `thread-per-request`; the error names both. `slots` is 32 or 200; `app_fields` is the app node's `concurrency`, `proc` and, for a thread per request, `hold: call`.                                                                                                           |
| `Style::summary`  | The `Chose: ...` line `init` prints in text mode (`event loop, 32 slots` or `thread per request, 200 slots`, queue 100, 30 s timeout, "estimates; edit kaanal.yaml").                                                                                                                                                                                                                  |
| `endpoint_line`   | One `endpoints:` line for a route key. `GET` whose path (trailing `/` ignored) ends in `}` is `read` through `cache` then `database`; any other `GET` is `scan` through `database`; `POST`, `PUT`, `PATCH`, `DELETE` are `write` through `database`; any other method gives `None` (no entry, the default chain applies). The key is a JSON string, a valid quoted YAML key.           |
| `traffic_section` | The `traffic:` block (RULES 58): one profile `peak`, `rps: 100`, `duration: 30s`, a journey per route `endpoint_line` covers (GET weight 3, POST/PUT/PATCH/DELETE weight 1), at most 64 (a profile's limit), with a one-line estimate comment. Empty when no route gets an entry, because a profile needs a journey.                                                                   |
| `render_config`   | The whole file: schema header, `port`, `locale`, the estimate comment, gateway (`256` slots, queue 100, `proc: 2ms`, `timeout: 30s`), the service (spec, style fields), database (postgres), cache (redis), three edges with `net: { p50: 1ms, p99: 3ms }`, and the `endpoints:` block with its own estimate comment (omitted when no route gets an entry), then the `traffic:` block. |

The numbers equal `kaanal_core::presets::starter` for the gateway and the service (test `the_numbers_are_the_studio_starter_numbers`). The route list comes from `kaanal_server::spec_routes`, the reader `kaanal endpoints` uses; `init/mod.rs` (`build_config`) renders once without `endpoints:` to read the routes, then again with them.
