# `crates/kaanal-core/src/scenario.rs`

Named chaos scenarios and the stack that layers them under the live chaos. Pure data and rules: where scenarios come from (the config, `scenarios/*.yaml`, the control API) is the server's business ([../kaanal-server/scenarios.md](../kaanal-server/scenarios.md)). The model is explained in [../../chaos.md](../../chaos.md).

## What it does

- Defines what a scenario is (`Scenario`), the set of known ones (`ScenarioSet`, with name rules and bounds), and the ordered stack of active ones plus the live layer (`ChaosStack`).
- Turns a parsed scenario (`ScenarioConfig` from [config.md](config.md)) into layers, checking it against the topology and the compiled endpoints (`resolve_scenario`).
- `ChaosStack::compile` folds the active scenarios, bottom to top, and the live state on top, into the `EffectiveChaos` the executor reads ([chaos.md](chaos.md)).

| `ScenarioError`                                                      | struct | A problem found while resolving a scenario: `path` (`chaos`, entry index, field), `value` (point at the value, not the key), `message`, and `not_found` (the entry names an unknown node or endpoint: the control API answers 404 for that, 400 for the rest). `located(prefix)` makes it a `Located`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| `validate_scenario_shape(&ScenarioConfig)`                           | fn     | Every check that needs neither topology nor endpoints (`limits`, the chaos and pins counts, a scenario with neither `chaos` nor `pins`, per chaos entry: target, endpoint shape, kind, something set, ranges, duplicate keys; per pin: endpoint shape, `check_entry` for its state, no endpoint twice). `resolve_scenario` runs it first; `kaanal scenario load` runs it alone so errors read `file:line:col`.                                                                                                                                                                                                                                                                                                                                                                                      |
| `resolve_scenario(name, &ScenarioConfig, topo, endpoints, empty_ok)` | fn     | Returns `(Scenario, warnings)` or the first `ScenarioError`. Runs `validate_scenario_shape` first, then looks each entry up: the node exists, the endpoint exists and has an entry node (unknown names are `not_found`), then each pin: the endpoint exists (`not_found`), is not a synthesized `HEAD`, has an entry node, and for `empty` passes `empty_ok(endpoint)` (the server's answer to "is there an empty form?"; core cannot read schemas). Warnings: a kind or status without a rate, and a `node` + `endpoint` pair the chain never visits.                                                                                                                                                                                                                                              |
| `ChaosStack`                                                         | struct | `active` (names, bottom to top, private) and `live` (private; `live()` and `live_mut()`) on top. `activate(set, name)` (push or move to top), `deactivate(name) -> bool`, `set_active(set, names)` (the whole stack, atomic, repeated names keep their last position, an unknown name changes nothing), `prune(set)` (drop names no longer defined; the server's undefine calls it), `clear_scenarios()`, `live_pins()` / `live_pins_mut()` (the live `PinLayer`), `clear_all()` (scenarios, live chaos and live pins), `active()`, `compile(set)` (skips active names no longer defined), `compile_pins(set)` (folds the active scenarios' pins bottom to top and the live pins last into `EffectivePins`; the later layer replaces an endpoint's pin whole, a `success` pin is kept so it masks). |

**Private:** `check` (name and bound), `visits(endpoint, node)` (does the chain visit the node; walks shared bodies once each, the owner and entry node count as visited), `resolve_entry`, `err`, `missing`.

## Rules worth knowing

- A scenario holds chaos, pins or both. `chaos` is optional; a scenario with neither is the "needs at least one of chaos or pins" error. Pins count toward `MAX_ENTRIES` with the chaos entries. `limits:` still parses and is rejected as "not supported yet".
- Scenario entries never carry `mode`; they are always `merge`. Override exists only on the live layer.
- `resolve_scenario` knows nothing about the file system; positions for inline errors are built by the caller with `ScenarioError::located`.
- The server must call `prune` (or `deactivate`) after `ScenarioSet::remove`, so `active()` never lists a scenario that does not exist.
