# `crates/kaanal-core/src/pin.rs`

UI-state pins: force an endpoint to answer as `loading`, `empty`, `error`, `slow` or `success`, layered like chaos (scenarios, then the live layer on top). Pure data and rules. The chain still runs under a pin; the server decides the response from the `Outcome` of `resolve` ([../kaanal-server/pins.md](../kaanal-server/pins.md), [../kaanal-server/mock.md](../kaanal-server/mock.md)). For users: [../../../web/pins.md](../../../web/pins.md).

## Rules worth knowing

- **No merging across layers.** The highest layer naming the endpoint wins state, status and delay together. Scenarios fold bottom to top in activation order, the live layer last ([scenario.md](scenario.md), `compile_pins`).
- **`states:` is validated like a pin** (`check_entry`), and `success` and unknown keys are refused, so `states.loading.status` is an error. A `body` on `loading` or `slow` is refused at compile ("a loading override takes no body"): those states answer as the route normally does.
- **A pin adds no random draw.** Its delay reaches the plan only through `ChainRequest.pin_delay` ([exec.md](exec.md)).
