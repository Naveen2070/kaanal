# `crates/kaanal-core/src/chaos/`

**Layout (R3.8):** `mod.rs` holds the state types (kinds, `NodeChaos`, `ChaosLayer`, `ChaosKey`, `ChaosState`); `resolve.rs` holds the compiled form (`Resolved`, `EffectiveChaos`, `compile_layers`). Public paths are unchanged.
`chaos/link.rs` holds the rules of chaos on an edge (`ChaosLayer::check_link`, `link_only_field`).

Chaos state types: the user-controlled failure knobs, their sparse layers and the compiled form the executor reads. The whole model (kinds, layers, banding, override) is explained in [../../chaos.md](../../chaos.md).

## What it does

Holds chaos settings as sparse **layers** under a **key** (a node, an endpoint, or a node reached through one endpoint). A `ChaosState` is one such layer set: the live layer, or the layers of one scenario ([scenario.md](scenario.md)). Written by the control API (`PUT/DELETE /__kaanal/chaos...`) and by scenarios, then **compiled** (`compile_layers`) into an `EffectiveChaos`: per key, one `Resolved` with the latency, the outage flag and the banded faults. The chain executor reads only the compiled form, with borrowed O(1) lookups. Chaos is never a node field in `kaanal.yaml`: scenarios come from `scenarios:` and `scenarios/*.yaml`, everything else is runtime state.

Private helpers: `resolve_entries` (sort by layer rank then specificity, sum latency, OR `down`, push one fault per layer with `error_rate > 0`, then clamp), `entries_of` (one key across the layers, cut at the last `replace`), `Resolved::push` (running union for the bands; folds into the last band past 8).

## Behaviour notes

- A fault's kind and status come from the layer that sets its rate; the unset half defaults to `status` / 503. A layer with a kind but no rate contributes nothing.
- The endpoint-wide key stays out of `visit`: it applies once at the front door and is read with `EffectiveChaos::endpoint()`.
- `dense` is for the single-layer GET view only; do not use it for executor logic.

## Invariants

- Every driver validates before anything lands here (the control API on the stored layer, scenarios on load and on `PUT`, the simulator on its whole `ChaosState` through `first_error`); the executor trusts the values. `AppState::publish` re-checks the compiled rates and statuses before a swap.
- The executor reads this through an `Arc<Effective>` snapshot behind a `RwLock` in `AppState` (see [../kaanal-server/state.md](../kaanal-server/state.md)); every write compiles once.
