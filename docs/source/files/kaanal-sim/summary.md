# `kaanal-sim/src/summary/` (`mod.rs`, `series.rs`)

`summarize(topo, endpoints, cfg, report) -> Summary` folds a finished `SimReport` into what Studio shows, so the hop records can be dropped (a server run keeps summaries only). `NodeStats` is frozen (R1.48(5)); this is the structure beside it. It has no timing model: it only reads the records the engine produced.

- **Latency.** Exact nearest-rank p50, p95, p99 and the maximum from the sorted samples, overall and per stream, plus 19 log2 buckets from 0.25 ms (an overflow bucket last; `le_ms` is `None` there).
- **Per node and replica.** A visit is a `Proc`, `Op`, `CacheHit` or `CacheMiss` hop at `(node, replica)`; its queue wait is the record's wait. `offered_load` = summed hop time ÷ (slots × replicas × window), `None` for a node with no `concurrency` or `pool` (the engine's `utilization` is 0.0 there). `saturated` needs slots and then any of: offered load of 1.0 or more, measured utilization of 0.95 or more, or requests shed at the node (a full queue, a fired deadline). A node without slots is never saturated; deadlines that fire there get their own warning (a callee was slow). `offered_load` comes from recorded hop time, which a failure or a deadline cuts short, so it undercounts then; `utilization` (the engine's busy slot-time, also `SimReport::replica_utilization` and `link_utilization`) does not. A monolith's `Proc` and `Op` hops are one visit. Mean wait and visits leave out a request cancelled while it still queued.
- **Per link.** Each edge with a `bandwidth`: transfers (request and response each), mean wait, offered load = transfer time ÷ window.
- **Expected visits.** `expected_visits_per_s` comes from core's `visits_per_s` over the streams' endpoints and rates; failures cut chains short, so a failing run measures less.
- **Bottlenecks.** Nodes with visits, nodes with slots first, then by offered load, then by mean wait.
- **Warnings.** Fewer than 1000 reported requests: "p99 rests on N requests"; fewer than 100: p95 and p99 are noise; one line per saturated node or link. One run is one replication and has no confidence interval; the warnings say when the tail is noise.
- **Capacity.** `capacity_per_s` = slots × replicas ÷ mean busy time per visit (`None` without slots, visits or busy time); `saturates_at_req_s` = `capacity_per_s` × the mix's request rate ÷ its expected visits per second to the node, i.e. requests (not visits) per second the whole mix can reach before the node saturates (`None` without a capacity or when no request reaches the node); `headroom` = `1 - offered_load`, at least 0 (`None` without slots).
- **Links.** Per edge with a `bandwidth`: `offered_load` = transfer time over the window, `saturated` at 1 or more (or utilization 0.95 or more), and `saturates_at_req_s` = the mix's request rate ÷ `offered_load` (transfer time grows in step with the rate), `None` when nothing crossed the link. It is the link's counterpart of the node figure, so the UI can rank wires and nodes together.
- **Series (`summary/series.rs`).** One extra pass over the records; per node `series { window_s, busy, queue, latency }` over 60 windows of the reporting window (`window_s` = window ÷ 60, also for a run shorter than a second). `busy[i]`: summed hop time overlapping window `i` (a hop is split across windows by overlap, from `arrival + start` for `dur`) over slots × replicas × `window_s`, at most 1, empty without slots. `queue[i]`: the longest queue at a join in window `i`, derived from the hop wait intervals per replica (a hop that waited joins at `start - wait` and leaves at `start`; the join counts hops with `join <= t < leave`), max over replicas as `max_queue` is; a queue wait of zero (a hand-over at the same instant) and a request cancelled while queued (absent from the records) are not seen. `latency[i]`: counts of the node's own hop durations in 20 columns (the 19 bounded buckets and the overflow bucket, same bounds as `latency.buckets`) by the window the hop started in; hops starting after the end of the run (the drain) land in the last window, as do queue joins, so the columns sum to the hop count. The records hold only requests that arrived at or after warmup: with a warmup, early windows miss the hops of earlier requests, so `max(queue)` and the busy sum equal the engine's figures for warmup 0 only. `NodeStats` and the engine are untouched.
- **Label.** Always `relative what-if, not a prediction` (R6.5).

Tests: `tests/sim/summary.rs` (hand-computed M/M/1 load, replica split, link transfers, error kinds, visits against the engine counters, the empty window); `tests/sim/series.rs` (60 windows and busy sum against the engine's utilization, queue peak at saturation, no series without slots, capacity 122.4/s, headroom, latency columns sum to the hop count, a run under a window).
